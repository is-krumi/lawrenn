Lawrenn — Security & Data Protection Overview

How Lawrenn protects attorney-client data and firm information

Prepared: June 2026  |  Version 1.0  |  Confidential

1. Overview

Lawrenn is a legal practice management platform that handles sensitive attorney-client data including matter files, client PII, legal documents, call transcripts, and AI-generated insights. This document summarises the security controls implemented across the platform.

All security measures described below are implemented at the application and infrastructure level. Lawrenn is built on Next.js 15, Supabase (PostgreSQL), and deployed on Vercel. Third-party AI processing is performed via Anthropic's Claude API under a Data Processing Agreement.

2. Authentication & Identity

2.1 User Authentication

  • All user sessions are managed by Supabase Auth, which issues short-lived JWT access tokens.
  • Tokens are validated on every API request server-side — no request can access data without a valid, unexpired JWT.
  • Sessions are not persisted server-side; every server client is instantiated fresh per request with the user's token.

2.2 Business Membership Verification

Every data API route calls verifyBusinessAccess before executing any query. This function:

  • Parses the Bearer token from the Authorization header.
  • Checks the business_members table to confirm the user belongs to the requested business.
  • Also checks businesses.owner_id as a fallback for firm owners.
  • Returns HTTP 401 immediately if either check fails — no data is read or written.

This prevents any cross-firm data access even if a user has a valid JWT for a different firm.

3. Data Access Controls

3.1 Row-Level Security (RLS)

Supabase Row-Level Security policies are enabled on all core tables: documents, jobs, intelligence_conversations, intelligence_messages, and matter_contacts.

  • All direct table queries from application code use a user-scoped Supabase client (anon key + user JWT), not the service role key. RLS is therefore enforced as a second layer of defence on every query.
  • Even if application-level business checks were bypassed, the database would reject any query for rows outside the user's business.

3.2 Service Role Key Restrictions

The service role key (which bypasses RLS) is used only where technically required:

4. Document & Storage Security

4.1 Server-Side Signed URL Generation

Document download and preview URLs are never generated from the browser. All signed URL generation goes through the /api/documents/signed-url server endpoint, which:

  • Accepts a document_id (never a raw file path) from the client.
  • Verifies business membership via verifyBusinessAccess.
  • Fetches the file_path from the database server-side — the client never knows the storage path.
  • Generates the signed URL using the admin client with a 5-minute expiry.
  • Returns the URL only if all checks pass.

4.2 Unpredictable Storage Paths

Document storage paths use a cryptographically random UUID rather than a predictable timestamp:

  • Before: {businessId}/{timestamp}-{filename} — guessable within a time window
  • After: {businessId}/{uuid}.{ext} — 122 bits of entropy, not brute-forceable

Combined with server-side signed URL generation, an attacker who somehow learns the storage path still cannot obtain a valid URL without a legitimate authenticated session.

5. Encryption

5.1 Encryption in Transit

All traffic between clients, the Next.js server, Supabase, and third-party APIs (Anthropic, OpenAI) is encrypted via TLS 1.2+ (enforced by Vercel and Supabase).

5.2 Encryption at Rest — Document Content

Legal document text chunks stored in the embeddings table are encrypted at the application layer using AES-256-GCM before being written to the database:

  • Each chunk is encrypted with a unique random 96-bit IV — identical text produces different ciphertexts.
  • GCM mode provides authenticated encryption, detecting any tampering.
  • The encryption key is a 32-byte secret stored only in the server environment (DOCUMENT_ENCRYPTION_KEY), never in the database.
  • Decryption happens in the API layer before content is sent to the LLM — encrypted data never leaves the server.
  • A database dump alone is insufficient to recover document content; the server environment key is also required.

This protects deposition transcripts, contract terms, client PII, and other privileged content stored in the embeddings index.

5.3 Database Encryption at Rest

Supabase encrypts all data at rest at the storage layer (AES-256) by default, independent of application-level encryption.

6. AI & LLM Data Handling

6.1 Anthropic Data Processing Agreement

Lawrenn processes legal data through Anthropic's Claude API. Anthropic does not train on API inputs by default. A formal Data Processing Agreement (DPA) with Anthropic is in place, under which Anthropic acts as a data processor and Lawrenn (and the law firm) acts as the data controller.

6.2 Data Minimisation

Only the context necessary to answer the attorney's question is sent to the AI:

  • Matter AI queries include case type, status, attorney notes, AI summary, and relevant document chunks.
  • Direct client identifiers (phone number, address) are reviewed for inclusion on a need-to-know basis.
  • Document content sent to the AI is always decrypted in the server environment — encrypted ciphertext is never sent to external APIs.

6.3 Attorney-Client Privilege Considerations

Transmission of privileged communications to a cloud AI provider does not automatically waive attorney-client privilege when the disclosure is made in furtherance of the legal representation. Attorneys using Lawrenn should consult their state bar's guidance on AI tool use (see ABA Formal Opinion 512, 2024). The DPA with Anthropic supports the reasonable-measures standard required by ABA Model Rule 1.6.

7.2 Injection Prevention

  • All database queries use Supabase's parameterised query builder — no raw SQL string interpolation.
  • No user input is interpolated into SQL.
  • File names are not used in storage paths (UUID-based paths), preventing path traversal via crafted filenames.

8. Infrastructure & Deployment

8.1 Secrets Management

  • All secrets (Supabase service role key, OpenAI key, Anthropic key, document encryption key) are stored as environment variables in Vercel's encrypted secrets store.
  • Secrets are never committed to source control or logged.
  • The service role key is never exposed to the browser — all code that uses it runs server-side in Next.js API routes.

8.2 Deployment Platform

  • Hosting: Vercel — automatic HTTPS, DDoS protection, edge network.
  • Database: Supabase (PostgreSQL) — SOC 2 Type II compliant, data encrypted at rest and in transit.
  • Storage: Supabase Storage (S3-compatible) — files stored with server-side encryption.
